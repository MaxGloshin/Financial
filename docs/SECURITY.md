# SECURITY — Personal Finance PWA

> **Обновление 23.11.2026:** активная версия — локальный PWA без сервера, аккаунтов и API.
> Разделы про VPS, passkey, сессии, коды восстановления и серверный API относятся к
> возможному этапу 2 и сейчас **не применяются**. Актуально: хранение в IndexedDB,
> шифрованные резервные копии (AES-GCM + PBKDF2), угрозы устройства. См. [`LOCAL-MVP.md`](LOCAL-MVP.md).

> Модель угроз и меры защиты. Приложение хранит полную финансовую картину одного человека: балансы, долги, привычки, контрагентов. Утечка — это не «неприятно», это готовый профиль для социальной инженерии и мошенничества.

## 3. Threat model (STRIDE)

| Угроза | Сценарий | Мера | Остаточный риск |
|---|---|---|---|
| **Spoofing** | Подбор пароля / вход по украденному коду | Только passkey; паролей нет; коды восстановления одноразовые, Argon2id, rate-limit | Низкий |
| **Spoofing** | Фишинг домена | Passkey привязан к RP ID: на чужом домене не сработает. HSTS, отсутствие похожих доменов | Низкий |
| **Tampering** | Подмена операции в очереди | Серверная валидация + инварианты + audit; ingest-токен write-only | Низкий |
| **Tampering** | Прямой доступ к SQLite на VPS | Шифрование диска у провайдера, минимум сервисов, SSH только по ключу | Средний (доверие хостеру) |
| **Repudiation** | «Я этого не вводил» | Append-only audit log с actor и request_id | — |
| **Information disclosure** | Утечка БД | Шифрование бэкапов, минимум ПДн, нет аналитики | Средний |
| **Information disclosure** | XSS читает данные | CSP без `unsafe-inline`, нет сторонних скриптов, HttpOnly cookie | Низкий |
| **DoS** | Флуд на API/вход | Rate limit по IP и по аккаунту, fail2ban, Caddy limits | Низкий |
| **Elevation** | Обход авторизации | Все проверки на сервере; клиент не решает, что можно | Низкий |
| **Elevation** | Кража сессии | HttpOnly + Secure + SameSite, привязка к device, отзыв, короткий TTL для чувствительных действий | Низкий |

### 3.1. Ключевые сценарии атаки и ответ

**A. «Забыл пароль» → сброс через email.** Нет email-сброса вообще. Нет email в системе. Восстановление — коды + второй passkey. Это убирает целый класс атак (взлом почты → захват финансов).

**B. Кража iPhone.** Face ID не даёт passkey без биометрии. Cookie-сессия в контейнере приложения защищена кодом устройства. Серверная сессия отзывается из другого устройства. Ingest-токен отзывается. Данные на сервере не пострадали.

**C. Вредоносное расширение в Chrome на Windows.** Может прочитать DOM и сделать запросы от имени пользователя. Меры: CSP, отсутствие сторонних скриптов, SameSite, проверка Origin, шаг-ап для экспорта. Полностью не закрывается — это риск доверенного браузера. Рекомендация: отдельный профиль браузера только для финансов.

**D. Утечка ingest-токена из шортката.** Токен write-only, привязан к устройству, rate-limit 30/мин, все созданные операции помечаются `source=shortcut` и видны в аудите. Атакующий может насорить операциями, но не прочитать данные. Токен отзывается одной кнопкой.

**E. Компрометация VPS.** Диск зашифрован у провайдера (проверить условие), бэкапы зашифрованы клиентским ключом, в БД нет банковских номеров и паспортных данных. Пароль от банка не хранится никогда.

**F. Забыт passkey и потеряны коды.** Данные недоступны. Это осознанный компромисс: альтернатива — бэкдор, который ломает всю модель. Смягчение: два устройства + бумажные коды + инструкция.

## 4. Аутентификация

### 4.1. Passkey (WebAuthn)

- RP ID: `finance.example.ru` (или `example.ru` при желании разделять поддомены). **Нельзя менять после регистрации** — иначе все passkey станут недействительны.
- `residentKey: 'required'`, `userVerification: 'required'` для входа.
- `attestation: 'none'` — не нужна, меньше данных.
- `excludeCredentials` при регистрации — чтобы не создать дубль на том же аутентификаторе.
- Challenge: 32 байта, хранится на сервере, TTL 5 минут, одноразовый.
- Проверка: `expectedOrigin` строго равен origin приложения, `expectedRPID`, подпись, счётчик.
- Публичные ключи и `credentialId` — в БД. Приватные ключи никогда не покидают устройство.
- Минимум два passkey: iPhone (iCloud Keychain) и Windows Hello. UI настойчиво предлагает добавить второй.

Почему passkey, а не пароль:
- нет общего секрета, который можно украсть из БД;
- фишинг не работает (ключ привязан к домену);
- вход — Face ID / отпечаток, без ввода;
- работает в установленном iOS PWA, потому что всё на своём origin.

### 4.2. Первичная настройка (bootstrap)

Публичной регистрации нет. Первый passkey создаётся так:

1. При первом запуске сервер генерирует одноразовый `SETUP_TOKEN` и печатает его в консоль (или читает из `.env`).
2. Пользователь вводит токен на странице `/setup`.
3. Токен одноразовый, TTL 30 минут, после успеха удаляется.
4. Повторный `/setup` возвращает 404.

Альтернатива: разрешить setup только с localhost через SSH-туннель. Для деплоя «с нуля» удобнее токен в логах.

### 4.3. Сессии

| Свойство | Значение |
|---|---|
| Cookie (production) | `__Host-pf_sid` |
| Cookie (local, http) | `pf_sid` — без `Secure`, иначе браузер её отбросит |
| Атрибуты | `HttpOnly; SameSite=Lax; Path=/`; `Secure` только на HTTPS |
| Выбор имени | по `NODE_ENV`/`APP_ORIGIN`; на сервере стартует проверка, что production не использует local-имя |
| Содержимое | 32 случайных байта (base64url), **не JWT** |
| Сервер | `sessions(id_hash, user_id, device_id, created_at, last_seen_at, expires_at, revoked_at, ip_hash, ua_hash)` |
| TTL | 30 дней, скользящее продление при активности |
| Абсолютный максимум | 90 дней → повторный passkey |
| Отзыв | Кнопка «Выйти на всех устройствах», список активных сессий |
| Ротация | Новый `sid` при входе и при step-up |

Почему не JWT в localStorage: токен читается любым XSS и не отзывается. Cookie с серверной сессией отзывается мгновенно.

### 4.4. Step-up (подтверждение чувствительных действий)

Свежая WebAuthn-ассерция (< 5 минут) требуется для:

- экспорта всех данных;
- добавления/удаления passkey;
- просмотра кодов восстановления;
- смены парольной фразы бэкапа;
- удаления аккаунта;
- отзыва всех сессий.

Обычные операции (добавить расход) step-up не требуют — иначе приложение станет невыносимым.

### 4.5. Коды восстановления

- 10 кодов, каждый — 128 бит энтропии, формат `XXXX-XXXX-XXXX-XXXX`.
- В БД: scrypt(код, соль, N=2^15) — не SHA-256 и не открытый текст.
- Одноразовые: при использовании помечаются, показывается остаток.
- Показываются **один раз** при настройке; скачать/распечатать.
- Вход по коду → разрешает зарегистрировать новый passkey → код сгорает.
- Rate limit: 5 попыток/час на аккаунт, 20/час на IP.

### 4.6. Ограничение попыток входа

| Действие | Лимит |
|---|---|
| `/api/auth/login/options` | 20/10 мин на IP |
| `/api/auth/login/verify` | 10/10 мин на IP, 5/10 мин на аккаунт |
| `/api/auth/recovery` | 5/час на аккаунт, 20/час на IP |
| `/api/ingest/*` | 30/мин на токен |
| Остальной API | 300/мин на сессию |
| Экспорт | 3/час |

При превышении — `429` с `Retry-After`, экспоненциальная задержка, запись в лог безопасности (без сумм). После 10 неудачных попыток входа — временная блокировка аккаунта на 15 минут с уведомлением через push (если настроен).

### 4.7. Смена окружения и RP ID

Passkey математически привязан к RP ID. Между `localhost` и `finance.example.ru` он **не переносится**, и автоматический перенос не реализуется.

Правила:

1. `WEBAUTHN_RP_ID` и `WEBAUTHN_ORIGINS` — только из конфига, без значений по умолчанию в коде.
2. При старте сервер проверяет: production → RP ID является суффиксом origin, origin начинается с `https://`; local → разрешён `http://localhost:<port>`, RP ID `localhost`.
3. `passkeys.rp_id` хранится в строке. Вход выбирает только ключи текущего RP ID.
4. Ключ другого окружения → `409` с кодом `RP_MISMATCH` и текстом «Этот ключ создан для другого адреса. Войдите по коду восстановления и добавьте новый».
5. Мост между окружениями — **коды восстановления** (хэши в БД переносятся вместе с базой).
6. После переезда: войти по коду → зарегистрировать production-passkey на iPhone и Windows → отозвать локальные сессии.
7. Смена RP ID без сохранения БД = потеря доступа. Поэтому конфиг валидируется, а не «подставляется».
8. Старые ключи не удаляются автоматически: они остаются в аудите, но не используются.

## 5. Авторизация на сервере

Правило: **клиент не является источником прав**.

- Каждый запрос: `session → user_id → ownership check` для каждой сущности.
- Даже при одном пользователе проверка `user_id` присутствует — это защита от будущих ошибок и от инъекции чужого ID.
- Ingest-токен даёт доступ **только** к `/api/ingest/*` и только на запись. Чтение через него невозможно.
- Никаких «админских» эндпоинтов без отдельной проверки.
- Все ID — UUID; перебор не даёт преимуществ, но проверка владельца всё равно обязательна.
- Массовое присвоение (`mass assignment`) запрещено: входные схемы Zod перечисляют разрешённые поля явно.

## 6. Защита API

### 6.1. CSRF

- `SameSite=Lax` на сессионной cookie.
- Проверка `Origin`/`Referer` для всех `POST/PUT/PATCH/DELETE`: должен совпадать с `https://<host>`.
- Дополнительно: заголовок `X-Requested-With: fetch` обязателен для cookie-аутентифицированных мутаций (браузер не даст поставить его cross-origin без CORS-preflight).
- CORS: `Access-Control-Allow-Origin` не отдаётся вовсе (same-origin only). Preflight на чужой origin → отказ.
- Ingest-эндпоинты CSRF не подвержены (нет cookie), защищены bearer-токеном.

### 6.2. Валидация входа

- Zod-схемы на каждый эндпоинт, `strict()` — лишние поля отклоняются.
- Ограничения: длина строк (заметка ≤ 500), сумма ≤ 10⁹ копеек, дата в разумном диапазоне, enum-значения.
- Никакого `eval`, динамического SQL, шаблонной сборки запросов. Только параметризованные запросы Drizzle.
- Загрузка CSV: лимит 5 МБ, парсинг потоково, максимум 10 000 строк, отклонение при превышении.

### 6.3. Заголовки безопасности

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob:;
  font-src 'self';
  connect-src 'self';
  manifest-src 'self';
  worker-src 'self';
  frame-ancestors 'none';
  base-uri 'none';
  form-action 'self';
  object-src 'none';
  upgrade-insecure-requests;

Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Resource-Policy: same-origin
X-Frame-Options: DENY
```

`style-src 'unsafe-inline'` допустим только если Tailwind/Radix требуют; иначе — nonce. Скрипты — только свои, без CDN, без inline.

### 6.4. XSS

- React экранирует по умолчанию; `dangerouslySetInnerHTML` запрещён (линт-правило).
- Заметки — плоский текст, не Markdown/HTML.
- Имена категорий и контрагентов выводятся как текст.
- CSP блокирует inline-скрипты.
- Зависимости: lockfile, `npm audit` в CI, Dependabot, минимум пакетов.
- Нет сторонней аналитики, чатов, виджетов, шрифтов с CDN.

### 6.5. Ограничение размера и таймауты

- Тело запроса ≤ 1 МБ (кроме CSV — 5 МБ).
- Таймаут запроса 15 с.
- SQLite: `busy_timeout`, WAL, один писатель.
- Отключены лишние HTTP-методы; `TRACE` запрещён.

## 7. Шифрование

| Слой | Мера |
|---|---|
| Транспорт | TLS 1.2+ (Caddy), HSTS, только HTTPS, редирект с HTTP |
| Диск VPS | Шифрование у провайдера (уточнить условие тарифа) |
| БД | Не шифруется построчно в MVP (SQLite). Компенсация: шифрованные бэкапы + минимум ПДн |
| Бэкапы | AES-256-GCM, ключ из парольной фразы (scrypt или Argon2id, ≥ 12 символов), соль + nonce в заголовке файла |
| Экспорт пользователю | Тот же формат, что бэкап |
| Локальный кэш | Опционально: AES-GCM с ключом из PIN (см. §9) |
| Секреты | `.env` 600, не в git, не в логах, не во фронтенде |

Парольная фраза бэкапа хранится **отдельно** от файла бэкапа. Иначе шифрование бессмысленно.

## 8. Логи и приватность

### 8.1. Что логируем

- `request_id`, метод, путь, статус, длительность.
- `user_id` (внутренний), `session_id` (хэш), `device_id`.
- Ошибки: код, стек (только на сервере), без payload.

### 8.2. Что НЕ логируем

- Суммы, описания, имена контрагентов, категории.
- Тела запросов и ответов.
- Cookie, токены, коды восстановления.
- Полные IP (храним усечённый/хэшированный, только для rate-limit и аудита).
- User-Agent целиком (только `ua_hash`).

### 8.3. Хранение

- Логи приложения — 14 дней, ротация.
- Лог безопасности (входы, отзывы, ошибки авторизации) — 90 дней, отдельный файл, без финансовых данных.
- `audit_log` в БД — бессрочно, но только действия пользователя, без секретов.
- Нет отправки логов в сторонние сервисы.

### 8.4. Трекеры

Их нет. Ни аналитики, ни пикселей, ни crash-reporting с внешним SDK. Метрики — только собственные счётчики на сервере.

## 9. Офлайн-данные и IndexedDB

### 9.1. Что хранится

- Кэш сущностей (счета, операции, категории).
- Очередь `outbox` с операциями.
- Настройки UI.
- **Никаких токенов.** Сессия — только HttpOnly cookie.

### 9.2. Риски

| Риск | Мера |
|---|---|
| Чтение через devtools на разблокированном устройстве | Экран блокировки приложения (PIN/biometric) после N минут в фоне; опциональное шифрование кэша |
| Извлечение данных с устройства | Шифрование кэша (опция), шифрование диска ОС |
| XSS читает IndexedDB | CSP, отсутствие сторонних скриптов; полная защита невозможна в браузере |
| Вытеснение данных | `persist()`, сервер как истина, snapshot |
| Устаревшие данные после выхода | Очистка IndexedDB и CacheStorage при logout |

### 9.3. Опциональное шифрование локального кэша

Предлагается как настройка (по умолчанию выключено):

- Ключ = Argon2id(PIN, salt), 6–8 цифр → слабо, поэтому PIN только как «замок», не как единственная защита.
- Данные шифруются AES-GCM на запись, расшифровываются в память.
- При потере PIN кэш невосстановим; данные на сервере целы → snapshot.
- Честная оценка: защищает от forensic-извлечения, не защищает от активного XSS в момент работы.

### 9.4. Блокировка приложения

Требование: защитить данные при чужом доступе к разблокированному устройству, **не превращая вход в пытку**.

| Параметр | Значение |
|---|---|
| По умолчанию | блокировка после 15 минут неактивности |
| Настройка | 5 / 15 / 30 / 60 минут / никогда |
| При уходе в фон | проверка при возврате; блокировка только если таймаут истёк |
| Немедленно | кнопка «Заблокировать» |
| Разблокировка | WebAuthn-ассерция с `userVerification: required` |
| Если ассерция невозможна | «Войти заново» / «Код восстановления» |
| Если сессия истекла | полный вход, затем разблокировка не нужна |

Почему не PIN при каждом открытии:

- сессия живёт 30 дней; требовать секрет при каждом возврате — значит наказывать за нормальное использование;
- люди отключают защиту, если она мешает;
- PIN на 4–6 цифр даёт мало энтропии и создаёт ложное чувство безопасности;
- WebAuthn UV (Face ID / Windows Hello) сильнее и не требует запоминания.

Ограничения iOS PWA:

- WebAuthn в установленном приложении работает, UV — Face ID или код-пароль устройства.
- Нет фоновых таймеров: проверка выполняется при возврате в приложение, а не «пока оно закрыто».
- Промпт passkey требует жеста: на экране блокировки есть кнопка, автозапуска нет.
- Отмена промпта не блокирует приложение навсегда: есть альтернативные пути входа.

Честная оценка: это **UI-замок**, а не шифрование. Он не защищает от XSS, вредоносного расширения или forensic-извлечения. Криптографическая защита локального кэша — отдельная опция (этап позже), и тогда это будет явно написано в настройках.

## 10. Секреты и токены

| Секрет | Где | Защита |
|---|---|---|
| `SESSION_SECRET` | `.env` | 32+ байта, не в git |
| `SETUP_TOKEN` | `.env` / консоль | Одноразовый, TTL 30 мин |
| Ingest-токен | Shortcuts + БД (SHA-256) | Write-only, per-device, отзываемый |
| VAPID private key | `.env` | Не в git |
| S3-ключи | `.env` | Только запись в бакет бэкапов |
| Парольная фраза бэкапа | Менеджер паролей + бумага | Не на сервере |

Ingest-токен в Shortcuts — принятый компромисс. Он даёт только запись, ограничен по частоте, все операции атрибутируются и отзываются. Альтернатива (полноценный OAuth для Shortcuts) невозможна без нативного приложения.

## 11. Восстановление после потери устройства

| Сценарий | Действия | Результат |
|---|---|---|
| Потерян iPhone | Войти с Windows (passkey) → «Устройства» → отозвать сессию iPhone и ingest-токен | Доступ есть, потерянное устройство отключено |
| Потерян iPhone и Windows | Вход по коду восстановления → новый passkey | Доступ восстановлен, код сгорел |
| Потеряны все passkey и коды | Нет входа | Данные на сервере целы, но доступ закрыт. Восстановление только через SSH-доступ к VPS и ручную замену passkey владельцем сервера |
| Потерян VPS | Новый VPS → docker compose up → restore из бэкапа | RTO ≤ 30 мин |
| Потерян VPS и бэкапы | Локальный экспорт (если делался) | Частичное восстановление |
| Забыт PIN локального кэша | Вход заново → snapshot с сервера | Кэш потерян, данные целы |

Инструкция по восстановлению хранится офлайн (распечатка) и в менеджере паролей.

## 12. Мониторинг и реагирование

- `/api/health` — БД, диск, время.
- Внешний uptime-чек (бесплатный, например UptimeRobot) — только факт доступности, без данных.
- Оповещение о: 5xx, росте 401/429, ошибках миграции, заполнении диска > 80%.
- Ежедневная проверка: бэкап создан, размер адекватен, restore-тест прошёл.
- При подозрении на компрометацию: отозвать все сессии, ротировать ingest-токены, сменить S3-ключи, проверить audit_log, восстановить из бэкапа при необходимости.

## 14. Остаточные риски (приняты)

1. **Доверие хостеру.** Провайдер VPS имеет доступ к диску. Компенсация: шифрование диска (если есть), отсутствие особо чувствительных данных, шифрованные бэкапы.
2. **Доверие браузеру.** Вредоносное расширение может действовать от имени пользователя. Компенсация частичная.
3. **Нет E2E-шифрования БД.** Осознанно: сервер должен считать агрегаты и применять инварианты. E2E сделал бы аналитику и синхронизацию значительно сложнее.
4. **Passkey = единая точка отказа.** Компенсация: два устройства + коды + SSH-доступ.
5. **SMS-парсинг ошибается.** Компенсация: `needs_review`, undo, аудит.
6. **Один сервер.** Компенсация: бэкапы, быстрый restore, мониторинг.
