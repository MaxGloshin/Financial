## 1. Требования и ограничения

### 1.1. Функциональные

- Один пользователь, без публичной регистрации.
- Счета: наличные, дебет, кредитка, накопления, долги мне, неликвидные активы.
- Операции: доход, расход, перевод, погашение кредитки, возврат долга, корректировка.
- Подработки: выручка, себестоимость, материалы, прибыль, незавершённые заказы.
- Бюджет: адаптивное распределение, а не фиксированные проценты.
- Кредитка: лимит, долг, минимальный платёж, платёж для льготы, даты, ставка.
- Аналитика, прогноз, безопасная сумма на день/неделю, цели.
- Undo, редактирование, история изменений.
- Экспорт и резервное копирование.
- Финансовый помощник с объяснением расчётов (без обязательного ИИ).

### 1.2. Нефункциональные

| Свойство | Цель |
|---|---|
| Быстрый ввод | открыть → сумма → категория → сохранить |
| Офлайн | полноценная работа с операциями без сети |
| Синхронизация | без потерь и без дублей; явный статус |
| Доступность из РФ | без VPN (production) |
| Стоимость | ≤ 700 ₽/мес (после переноса на VPS) |
| Безопасность | passkey, HttpOnly-сессии, серверная авторизация |
| Восстановление | потеря устройства не означает потерю данных |
| Поддержка | один человек, минимум движущихся частей |
| Точность денег | только целые копейки |

### 1.3. Ограничения, принятые осознанно

- Нет фоновой синхронизации на iOS → очередь уходит при открытом приложении.
- Нет автоматического чтения банковских push → только SMS (платно, позже) или файл.
- Нет официального банковского API для физлиц в РФ.
- Нет публичной регистрации → первичная настройка через одноразовый setup-токен.
- SMS-интеграция **не входит в текущий объём**: сначала воспроизводимый тест Shortcuts.

### 1.4. Два окружения

| | `local` (сейчас) | `production` (позже) |
|---|---|---|
| URL | `http://localhost:5173` | `https://finance.<домен>.ru` |
| WebAuthn RP ID | `localhost` | `finance.<домен>.ru` |
| WebAuthn Origin | `http://localhost:5173` | `https://finance.<домен>.ru` |
| API | `http://localhost:3000` | тот же origin, `/api` |
| БД | `./data/dev.sqlite` | `/data/finance.sqlite` |
| Секреты | `.env.local` | `.env` на сервере |
| Бэкапы | локальные снапшоты | Litestream + S3 в РФ |
| Публикация | нет | только после согласия пользователя |

**Правило:** ни один адрес, RP ID, секрет или путь не хардкодится. Всё — через переменные окружения. Кодовая база одна.

## 2. Варианты архитектуры

### Вариант A. «Российский VPS + SQLite» — **выбран**

```
iPhone (PWA) ──┐
               ├── HTTPS ──> Caddy ──> Node.js/Fastify ──> SQLite (WAL)
Windows (PWA) ─┘                          │
                                          ├── Litestream → S3 (РФ, отдельно от VPS)
                                          └── Cron: регулярные операции, push
```

Сейчас тот же стек запускается локально: `node` + Vite, без Caddy и без домена.

**Плюсы:** доступно из РФ; ~300–700 ₽/мес; полный контроль; бэкап — файл; нет vendor lock-in; локальная разработка полностью совпадает с production по коду.
**Минусы:** обновления ОС и uptime на вас; один сервер — точка отказа (снимается бэкапами и RTO).

### Вариант B. «Cloudflare Workers + D1» — резервный

Технически элегантен, но **троттлинг Cloudflare в РФ с 06.2025** (16 КБ на соединение) и блокировки `workers.dev` делают его непригодным как основной путь к финансовым данным. Оставляем как документированную альтернативу для случая, если доступность из РФ изменится.

### Вариант C. «Managed Postgres + serverless frontend»

Отклонён: два вендора, пауза free-проектов, слабая предсказуемость из РФ, офлайн-синхронизация всё равно пишется вручную.

### Сравнение

| Критерий (вес) | A | B | C |
|---|---|---|---|
| Доступность из РФ (30%) | 5 | 2 | 3 |
| Стоимость (20%) | 4 | 5 | 4 |
| Безопасность (20%) | 5 | 5 | 4 |
| Простота поддержки (15%) | 3 | 5 | 4 |
| Контроль и переносимость (15%) | 5 | 2 | 2 |
| **Взвешенно** | **4.50** | **3.65** | **3.40** |

### Поток записи (этап 2, онлайн)

1. Пользователь нажимает «Сохранить».
2. Клиент валидирует Zod-схемой.
3. `POST /api/transactions`.
4. Сервер в одной транзакции: проверка → проводки → `audit_log` → ответ.
5. Клиент инвалидирует кэш, показывает тост с Undo.

### Поток записи (этап 3, офлайн)

Очередь `outbox` в IndexedDB, `opId`, идемпотентный `POST /api/sync/push`, pull по курсору. Детали — §6.

## 5. Модель данных

### 5.1. Деньги

- Всё — **целые копейки**: `amount_minor INTEGER`.
- Валюта: `currency TEXT` (`RUB`).
- В JSON суммы передаются **строкой** (`"12345"`), чтобы не терять точность.
- Парсинг: `"1 234,56"` → `123456`; `"250"` → `25000`; мусор → ошибка.
- Запрещено: `parseFloat`, `* 100`, деление денег, хранение рублей с плавающей точкой.
- JavaScript `number` безопасен до 9·10¹⁵ копеек — с запасом.

### 5.2. Двойная запись

Каждая операция — набор проводок, сумма которых равна нулю.

| Операция | Проводки | Результат |
|---|---|---|
| Расход 250 ₽ | Счёт −250, Категория-расход +250 | Расход +250, баланс −250 |
| Доход 13 000 ₽ | Счёт +13 000, Категория-доход −13 000 | Доход 13 000, баланс +13 000 |
| Перевод 1 000 ₽ | Счёт A −1 000, Счёт B +1 000 | Ни дохода, ни расхода |
| Платёж по кредитке 5 000 ₽ | Дебет −5 000, Кредитка +5 000 | Долг −5 000, расхода нет |
| Возврат долга 15 000 ₽ | «Долг мне» −15 000, Дебет +15 000 | Долг закрыт, дохода нет |
| Корректировка +100 ₽ | Счёт +100, Категория «Корректировка» −100 | Вне доходов/расходов |

Инвариант: `SUM(ledger_entries.amount_minor) = 0` для каждого `transaction_id`.

### 5.3. ER-диаграмма

```
users 1───n passkeys (rp_id!)
  │        sessions
  │        recovery_codes
  │        api_tokens (позже)
  │
  ├──1──n accounts ──1──n ledger_entries ──n──1 transactions
  │           │                                   │
  │           └── credit_statements               ├── project_id ──> projects
  │                                               └── import_batch_id
  │
  ├──1──n categories (self-ref parent_id)
  ├──1──n budgets
  ├──1──n debts ──> account (receivable/payable)
  ├──1──n goals
  ├──1──n recurring_rules
  ├──1──n planned_inflows
  ├──1──n templates
  ├──1──n import_batches ──1──n import_rows
  ├──1──n audit_log
  └──1──n app_settings
```

### 5.4. Ключевые таблицы

#### `accounts`
`id, name, type (cash|debit|savings|credit|receivable|payable|asset_illiquid|investment), currency, credit_limit_minor, interest_rate_bp, statement_day, payment_due_day, is_liquid, is_archived, sort_order, created_at, updated_at, deleted_at`.

Баланс не хранится — вычисляется из проводок.

#### `categories`
`id, name, kind (income|expense|adjustment), parent_id, icon, color, is_system, sort_order, monthly_target_minor`.

#### `transactions`
`id, kind (expense|income|transfer|credit_payment|debt_payment|refund|adjustment), occurred_at, description, project_id, source (manual|voice|sms|csv|recurring|shortcut), source_ref, import_batch_id, review_status (ok|needs_review|duplicate_suspect|ignored), created_at, updated_at, deleted_at`.

#### `ledger_entries`
`id, transaction_id, account_id NULL, category_id NULL, amount_minor`, `CHECK ((account_id IS NULL) <> (category_id IS NULL))`.

#### `passkeys`
`id, user_id, rp_id, public_key, counter, transports, label, created_at, last_used_at`.

> `rp_id` хранится **явно**. Это защищает от путаницы между localhost и production и делает невозможным «молчаливое» использование ключа не в том окружении.

#### `credit_statements`
`id, account_id, period_start, period_end, due_date, grace_end_date NULL, total_due_minor NULL, min_payment_minor NULL, paid_minor, status (open|paid|overdue|unknown), note`.

#### `templates`
`id, name, kind, amount_minor, account_id, category_id, icon, sort_order, usage_count`.

Шаблон — это не операция. Он создаёт операцию по тапу, но не влияет на баланс.

#### `planned_inflows`
`id, name, amount_minor, expected_date NULL, window_start NULL, window_end NULL, confidence (confirmed|likely|possible), note`.

`possible` (подарок) **никогда** не считается гарантированным доходом.

#### `app_settings`
`key, value` — таймаут блокировки, цель бюджета, тема, флаги.

#### `audit_log`
`id, at, actor, action, entity, entity_id, before_json, after_json, request_id`.

Только добавление. Никогда не удаляется через API.

#### `webauthn_challenges`
`id, user_id NULL, type (register|login|unlock), challenge, expires_at, used_at`.

Одноразовые, TTL 5 минут, хранятся в БД (переживают рестарт).

### 5.5. Импорт: дедупликация и сверка

Импорт не входит в этапы 0–2, но модель и правила фиксируются сейчас, чтобы ядро не пришлось переделывать.

**Порядок:**
1. Файл → `import_batches` (status `uploaded`).
2. Парсинг → `import_rows` (сырая строка + нормализованные поля).
3. Классификация каждой строки:
   - `new` — нет совпадений;
   - `duplicate_exact` — совпал `external_id` банка или точный ключ;
   - `duplicate_fuzzy` — та же сумма и счёт, дата ±1 день, похожее описание;
   - `possible_manual_duplicate` — совпадает с ручной операцией;
   - `invalid` — не хватает полей.
4. Предпросмотр: пользователь видит категории и может исключить строки.
5. Коммит: создаются только `new`; спорные получают `review_status='needs_review'` и **не влияют** на отчёты до подтверждения (или влияют с явной пометкой — решается в этапе 7).
6. Сверка: сравнивается баланс после импорта с заявленным банком. Расхождение показывается числом.

**Правила:**
- Точный ключ: `sha256(account_id | date | amount_minor | normalized_description)`.
- `external_id` (если банк даёт) приоритетнее хэша.
- Никогда не сливать автоматически ручную и импортированную операцию.
- Никогда не удалять «дубль» без подтверждения.
- Повторная загрузка того же файла не создаёт новых операций.

## 6. Синхронизация (этап 3)

### 6.1. Принципы

1. Сервер — источник истины.
2. Клиентские ID (UUIDv7) — нет временных идентификаторов.
3. `opId` на каждую операцию, сервер помнит применённые.
4. Операция применяется целиком или никак.
5. UI всегда показывает статус: синхронизировано / ждёт / ошибка.
6. Денежные конфликты решает человек.

### 6.2. Протокол

```
POST /api/sync/push { deviceId, ops: [{ opId, entity, entityId, op, baseRev, payload }] }
→ { results: [{ opId, status, rev, server?, error? }], cursor }

GET /api/sync/pull?since=<cursor>&limit=500
→ { changes: [...], cursor, hasMore }

GET /api/sync/snapshot
→ полное состояние + курсор
```

### 6.3. Конфликты

| Ситуация | Поведение |
|---|---|
| Повторный `opId` | `duplicate`, вернуть сохранённый результат |
| Создание существующей сущности | Идемпотентный успех |
| Update, неденежные поля | Автослияние + audit |
| Update, денежные поля | `conflict` → экран сравнения |
| Delete после чужого update | `conflict` |
| Похожие операции из разных источников | Не сливать, пометить «возможный дубль» |

## 7. Кредитная карта

- `type='credit'`, баланс отрицательный (= долг).
- `credit_limit_minor` — отдельно. Доступный лимит = лимит + баланс.
- Собственные средства и кредитный лимит **не смешиваются**.
- `credit_statements` — по одной на период.
- `grace_end_date` — отдельное поле, может быть `NULL`.
- **Запрещено** вычислять конец льготного периода как «дата платежа + N дней».

UI при неизвестных данных:

```
Выписка 29.11.2026 → оплатить до 22.12.2026
Сумма к оплате: не указана  [Уточнить]
Льготный период: не подтверждён  [Указать]
```

Предупреждения: за 7 дней, за 3 дня, в день платежа; приоритет — «сумма неизвестна».

## 8. Бюджет

Водопад от обязательств:

```
1. Подтверждённый доход периода
2. − Обязательные расходы
3. − Платежи по кредитам
4. − Минимальный резерв
5. = Свободно
6. Повседневные = Свободно − целевые накопления
7. Безопасно в день = Повседневные / оставшиеся дни
8. Накопления — только из положительного остатка
9. Инвестиции — только если резерв ≥ 3 месяцев обязательных
```

- Ориентир 6 000 ₽/мес — **редактируемая цель**, а не гарантия. Хранится в `app_settings.budget_target_minor`, помечается `is_tentative`.
- «Безопасно тратить» никогда не учитывает кредитный лимит и возможные подарки.
- Перерасход показывается, но не блокирует ввод.

## 9. Финансовый помощник

Детерминированный модуль. Без ИИ, без внешних API, без «магии».

### 9.1. Принципы

1. **Объяснимость.** Каждое число сопровождается формулой и списком входных данных.
2. **Честность.** Неподтверждённые поступления не считаются гарантированными.
3. **Осторожность.** Кредитный лимит — не деньги. Неликвид — не деньги.
4. **Детерминизм.** Одинаковые входы → одинаковые выходы. Тестируется property-тестами.
5. **Никаких рекомендаций без цифр.** «Потрать 420 ₽» всегда с расчётом.

### 9.2. Функции

| Функция | Вход | Выход |
|---|---|---|
| Безопасный остаток на день | ликвидные средства, обязательства, резерв, дни до дохода | сумма + формула |
| Прогноз до следующего гарантированного поступления | регулярные доходы, обязательные, кредит | дата, ожидаемый остаток, сценарии |
| Предупреждения по кредитке | выписка, дата, сумма, льгота | уровень, текст, что сделать |
| Оценка доступности покупки | сумма, счёт, дата | можно/рискованно/нет + последствия |
| Распределение нерегулярного дохода | сумма, обязательства, резерв | водопад по приоритетам |
| Объяснение расчёта | любой результат | `formula`, `inputs`, `assumptions`, `confidence` |

### 9.3. Формат ответа

```json
{
```

### 9.4. Запреты (проверяются тестами)

- `planned_inflows.confidence != 'confirmed'` не входит в доход.
- `accounts.type='credit'` не увеличивает ликвидные средства.
- `accounts.is_liquid=0` (Steam) не входит в безопасный остаток.
- Сумма к оплате по кредитке, если `NULL`, не подменяется нулём — это «неизвестно».
- Отрицательный безопасный остаток показывается как дефицит, а не обнуляется.

## 10. PWA, офлайн и блокировка приложения

### 10.1. PWA

- Precache shell, шрифты, иконки.
- Runtime: stale-while-revalidate для справочников, network-only для `/api`.
- Offline fallback: приложение открывается из IndexedDB.
- `navigator.storage.persist()` после первого входа.
- Обновление SW — по действию пользователя.
- Никаких сторонних скриптов и аналитики.
- Deep link `?quick=1` открывает быстрый ввод.

### 10.2. Блокировка приложения

Требование: **не требовать PIN при каждом открытии без необходимости.**

Модель:

| Параметр | Значение по умолчанию |
|---|---|
| Блокировка после неактивности | 15 минут (настройка: 5 / 15 / 30 / 60 / никогда) |
| Блокировка при уходе в фон | только если прошло больше таймаута |
| Немедленная блокировка | кнопка «Заблокировать» в настройках |
| Разблокировка | WebAuthn-ассерция (Face ID / Windows Hello) |
| Fallback | вход заново (если сессия истекла) |

Почему так:
- сессия живёт 30 дней, поэтому «открыл приложение» ≠ «нужен вход»;
- повторный Face ID каждые 2 минуты раздражает и приводит к отключению защиты;
- 15 минут — компромисс между бытовой безопасностью и удобством.

Реализация:
- клиент хранит только время последней активности (не секрет);
- при `visibilitychange` проверяет разницу;
- если превышено — оверлей блокировки, данные не показываются;
- разблокировка: `POST /api/auth/unlock/options` → WebAuthn → `POST /api/auth/unlock/verify`;
- сервер выдаёт короткоживущий флаг разблокировки (in-memory/сессия), не новую сессию.

Ограничения iOS PWA (исследованы):
- WebAuthn работает в установленном приложении, UV — Face ID или код-пароль устройства.
- Нет фоновых таймеров: проверка выполняется при возврате в приложение, а не «в фоне».
- Нет `navigator.vibrate`.
- Passkey-промпт требует жеста пользователя; поэтому на экране блокировки есть кнопка «Разблокировать», а не автозапуск.
- Если пользователь отменил промпт, показывается кнопка «Войти заново» и «Использовать код восстановления».

Что защищает: доступ к разблокированному телефону, случайный взгляд, чужой человек, взявший устройство.
Что не защищает: XSS, вредоносное расширение, forensic-извлечение (для этого позже — шифрование кэша).

## 12. Локальная разработка и перенос на VPS

### 12.1. Локально

```
npm install
npm run dev        # API :3000 + Vite :5173
npm test           # серверные и доменные тесты
npm run build      # сборка SPA
```

- `localhost` — безопасный контекст, поэтому **WebAuthn работает без HTTPS и домена**.
- Данные: `./data/dev.sqlite`.
- Setup-токен: `.env.local` (`SETUP_TOKEN=...`), печатается в консоль при первом запуске.
- Никаких внешних сервисов, ничего не публикуется.

### 12.2. Перенос на VPS (позже, по согласованию)

1. Купить домен `.ru` и VPS.
2. DNS → VPS, Caddy получает TLS.
3. `docker compose up` с тем же образом.
4. Перенести БД: `litestream restore` или копия файла.
5. Задать `WEBAUTHN_RP_ID=finance.<домен>.ru`, `WEBAUTHN_ORIGINS=https://finance.<домен>.ru`.
6. Войти по коду восстановления (passkeys от `localhost` недействительны).
7. Зарегистрировать production-passkey на iPhone и Windows.
8. Отозвать локальные сессии.
9. Включить бэкапы и мониторинг.

### 12.3. Миграция WebAuthn: правила

- Passkey привязан к RP ID навсегда. **Автоматический перенос невозможен и не делается.**
- `passkeys.rp_id` хранится; вход фильтрует по текущему RP ID.
- Ключ из другого окружения → понятная ошибка «Этот ключ создан для другого адреса. Войдите по коду восстановления и добавьте новый».
- Коды восстановления — мост между окружениями: они хранятся в БД (хэш) и работают после переноса.
- После переноса локальные ключи остаются в БД как исторические (для аудита), но не используются.
- Смена RP ID без переноса БД = потеря доступа. Поэтому RP ID фиксируется в конфиге и проверяется при старте.

### 12.4. Валидация конфигурации при старте

- `production`: `WEBAUTHN_RP_ID` должен быть суффиксом `WEBAUTHN_ORIGINS`, origin — `https://`.
- `local`: разрешён `http://localhost:*`, RP ID `localhost`.
- Несовпадение → сервер не стартует с внятной ошибкой.

## 13. Бэкапы и восстановление

| Что | Как | Частота | Где |
|---|---|---|---|
| Непрерывный | Litestream → S3 | постоянно | отдельный аккаунт/провайдер, не VPS |
| Ночной дамп | `VACUUM INTO` + gzip + AES-256-GCM | ежедневно | тот же S3 + локально |
| Месячный экспорт | JSON/CSV, шифрованный | по кнопке/месяц | устройство пользователя |
| Конфиг | `.env` | при изменении | менеджер паролей |

Требования:
- Бэкап **автоматический**, без ручных действий.
- **Зашифрован** (AES-256-GCM, ключ из парольной фразы через scrypt/Argon2id).
- **Хранится отдельно от сервера** (другой провайдер/аккаунт).
- Ключ не на сервере.
- Алерт, если бэкап не создан за 26 часов.
- **Тест восстановления** — ежемесячно, автоматически: контейнер, restore, smoke-тест (балансы, количество операций), отчёт.
- RPO ≤ 5 минут, RTO ≤ 30 минут.

Локально (сейчас): `npm run backup` создаёт шифрованный файл в `./backups` и проверяет его чтение. Это тренировка механизма до появления VPS.
